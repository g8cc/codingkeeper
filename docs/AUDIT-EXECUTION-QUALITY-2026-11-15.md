## 确认的问题

### P1：证据 Markdown 被误判为缺失，导致有产出也停炉（本次修复）

`codexc-headless` 原先只找连续的 `证据:` / `证据：`，不识别 Worker 实际输出的 `**证据**：…`。`sale` 的 `worker-op8k7k14.log` 确实含测试命令和 2/2 PASS，却因标签加粗进入 missing-evidence park。相反，空 `证据:` 和“没有证据:”原先又可能通过匹配。

修复仅规范识别行首证据标签的常见 Markdown、空白和冒号格式，拒绝空值及 `<依据>` 提示模板。它仍只是进入验收流程的条件，不能替代门禁或审查。

新增回归先在旧实现失败，再在修复后通过：

- 普通/加粗/代码样式/列表证据可识别，空值、模板和否定句不通过。
- 带 Markdown 证据的真实候选，仍必须经过一次 gate 和两次独立审查才产生 accepted.json。
- 既有动态回归继续检查：缺少证据时保留用户 staged/unstaged/untracked 内容和 Worker 提交，不验收、不重置。

### P1：产品自动门禁漏跑新增回归（已离线验证替换方案，未改现场）

`sale/.codingkeeper/gate.sh` 只发现 `tests/phase1–4`、functional/perf/quality/v2，漏掉历史验收中出现的 11 个 `scripts/`、`harness/tests/` 回归文件，其中包括热更新、客户端断连和录制回归。项目已有更完整的 `harness/run.mjs verify`，但自动执行链未接入它。

故障注入结果：在副本的 `scripts/` 新增一个必失败测试，单独运行退出 1，原 gate 却退出 0（54 个文件，275 tests，274 pass，1 skip）。这不是“可能漏跑”，是已经复现的漏检。

替换 gate 为项目现有 verify 入口后，同一个必失败测试被拦截：329 tests，1 fail，退出 1。移除故障夹具后再次通过该 gate：328 tests，327 pass，0 fail，1 skip，退出 0。建议补丁见 [`execution-audit/2026-11-15-sale-gate.patch`](execution-audit/2026-11-15-sale-gate.patch)。补丁只改变门禁入口，仍禁止真实模型；不重写业务测试，不降低阈值。

### P1：旧控制器确实丢弃过未验收候选，且有功能缺口留到今天

`sale` reflog 在 **2026-11-08 17:25:26–19:07:37（UTC+8）** 记录了 16 次重置到 `c1b0ba7`。当时控制器 `c4daacb` 引入的 idle 证据检查在缺失标记时执行 `git reset --hard baseline`，与时间及 Worker 记录吻合；这会同时丢掉候选提交和基线中的用户未提交内容。

该危险路径已在 **2026-11-13 的 `b66712b`** 删除，当前安装入口解析到真实 `codingKeeper` 目录的新版脚本。当前逻辑改为保留工作、停炉待查。本次没有再次执行或恢复任何硬重置。

必须区分：**这 16 次涉及未验收候选；本次核查的 28 个已验收 candidate 均仍在祖先链中。** 不能把事故描述为“16 个已验收修复全部丢失”。

不过，丢弃确实造成重复劳动和未收口的产品问题。将悬空提交 `a13f63a` 的信号退出回归放到当前隔离副本：**5 项中 3 通过、2 失败**。可观察到生成中向服务发 SIGTERM 后假 CLI 继续完成、私有临时目录残留。完整现有套件全绿仍不能发现这个已丢失的回归。

历史审查曾对该方向找出 undefined 子进程登记、error 路径未注销、700ms 退出早于 1.5s 强杀等具体缺陷，说明独立审查能阻止部分坏交付。也正因为候选多轮未收口，不应把悬空提交整包恢复后直接认定安全。

### P2：运行稳定性遥测不足以代表产品质量

`ck-quality-trend.py` 基于 journal 的审查轮数与 gate 重试率，`ck-morning.py` 基于 receipt 展示结果。它们不核验用户流程、回归发现范围或最终用户价值。

最后一份 `sale` receipt 的证据目录跨多次恢复，保留 8 份 review、5 份 gate 日志，而最终 journal 为“2 review rounds、0 gate retries”。它描述最终成功的运行段，不能作为这整段历史只付出两次审查、完全无重试的证明。

### P2：部分测试的声明大于实际断言

`scripts/generate-client-abort.test.mjs` 中名为 `alive` 的值探测的是测试进程自己的 `process.pid`，且调用方没有断言它，不能据此证明服务仍可处理下一次请求。本次确认的价值仅限于两条 CLI 路径收到终止信号、不再跑满，不扩称恢复链已经完整验收。

历史 `server-signal-shutdown.test.mjs` 的“忽略 SIGTERM 后应被强杀”用例等待最多 8 秒，而假 CLI 5 秒即可自然结束；仅靠最终“不存活”不能区分强杀与自然完成。两次离线复验都有真实失败（未收到 SIGTERM、目录残留），足以确认当前缺口，但将来修复时必须加强为启动就绪信号、早于自然结束的退出预算、失败时 finally 清理及进程/目录的双重断言，不能只让旧测试变绿。
